## 1. Modèle de données

### 1.1 Ontologie (`ontology_v2.json`) — par concept

| Champ | Direction | Sémantique | Sévérité |
|---|---|---|---|
| `negation_of: [ids]` | directionnel (existant) | "ce concept EST la négation de X" | — (sert au crédit, PAS une contrainte à part) |
| `excludes: [ids]` | **symétrique** | contradiction absolue (13 relations HARD) | `error` |
| `conflicts_by_default: [ids]` | **symétrique** (nouveau champ) | incompatibilité clinique habituelle (24 relations DEFAULT) | `warning` |
| `excludes_families: [ids]` | symétrique sur la descendance (existant) | famille entière exclue (ECG_NORMAL…) | `error` (inchangé) |

- Symétrie : une seule déclaration suffit (`A.excludes = [B]` implique
  `B exclut A`). Le moteur canonicalise ; les réciproques déclarées en
  double dans le JSON sont tolérées (dédupliquées au chargement).
- Aucun champ `exceptions:` dans l'ontologie (l'override golden suffit).

### 1.2 Golden (par cas) — statut d'un concept

Trois statuts dérivés du golden existant, **sans modifier son format** :

```text
ACCEPTED   le concept (ou un descendant/parent proche crédité) figure au
           mapping du cas avec statut present (validant / complementaire /
           descripteur)
FORBIDDEN  le concept figure au golden avec statut "absent" (V1) ou
           role "exclusion" (V2)
UNKNOWN    le concept n'apparaît pas dans le golden du cas
```

Champ optionnel nouveau, par cas, ajouté SEULEMENT au besoin :

```json
"allowed_cooccurrences": [["QRS_FINS", "BLOC_DE_BRANCHE"]]
```

(couvre le cas où deux concepts sont légitimes ensemble sur CE tracé mais
où l'un des deux n'a pas vocation à être exigé dans la correction.)

## 2. Nouveau module : `rag_pipeline/coherence.py`

Un module dédié, séparé de `scoring_v3.py` (qui reste le calcul
d'adéquation). ~150 lignes estimées.

### 2.1 Chargement des contraintes (canonicalisation)

```python
@dataclass(frozen=True)
class Constraint:
    pair: Tuple[str, str]          # tuple(sorted((A, B))) — canonique
    kind: str                      # "excludes" | "conflicts_by_default"
    severity: str                  # "error" | "warning"

def build_constraint_registry() -> Dict[Tuple[str, str], Constraint]:
    """Parcourt l'ontologie une fois ; canonicalise et déduplique.
    En cas de double déclaration contradictoire (A excludes B ET
    A conflicts_by_default B) : garde la plus sévère + log warning."""
```

Cache module-level (même pattern que `_NEGATION_MAP`).

### 2.2 Statut golden d'un concept

```python
def golden_status(concept_id, case_golden) -> str:  # ACCEPTED|FORBIDDEN|UNKNOWN
```

Règles :
- ACCEPTED si le concept est un golden_id du mapping avec statut present ;
  **extension hiérarchique** : également ACCEPTED si c'est un
  descendant direct d'un golden ACCEPTED (l'étudiant plus spécifique que
  le golden ne doit pas déclencher de conflit) — profondeur 3, mêmes
  helpers que `_get_all_children_recursive`.
- FORBIDDEN si statut "absent" / role "exclusion".
- UNKNOWN sinon.

### 2.3 Évaluation des contradictions intra-réponse

```python
@dataclass
class Contradiction:
    concept_a: str
    concept_b: str
    kind: str          # excludes | conflicts_by_default
    severity: str      # error | warning
    overridden: bool   # True si levée par le golden
    override_reason: str  # "golden_accepts_both" | "allowed_cooccurrence" | ""

def check_response_coherence(
    found_present: Set[str],       # concepts extraits statut=present UNIQUEMENT
    case_golden: dict,
) -> List[Contradiction]:
```

Algorithme (le pseudo-code validé dans la décision d'architecture) :

```text
pour chaque paire (A, B) de found_present × found_present, A < B :
    c = registry.get((A, B))
    si c est None : continuer
    si golden_status(A) == ACCEPTED et golden_status(B) == ACCEPTED :
        → Contradiction(overridden=True, reason="golden_accepts_both")
    sinon si (A, B) ∈ allowed_cooccurrences du cas :
        → Contradiction(overridden=True, reason="allowed_cooccurrence")
    sinon :
        → Contradiction(overridden=False, severity=c.severity)
```

Points de design :
- **Seuls les concepts `statut="present"` participent** — un concept nié
  ("pas de bloc de branche") ou en hypothèse ne contredit rien.
- Complexité : |found| ≤ ~15 concepts par réponse → 105 paires max,
  lookup O(1) — négligeable.
- Les contradictions overridden sont **retournées quand même** (traçables
  dans les rapports/audits) mais n'ont aucun effet de score.

## 3. Effets sur le score (intégration `neuro_grader.py`)

Réutilise la mécanique de caps EXISTANTE — pas de nouveau barème :

| Événement | Effet |
|---|---|
| Contradiction `error` non-overridden | cap `EXCLUSION_RANG_A_SCORE_CAP` (25) + `correspondance="incorrecte"` + entrée `elements_errones` |
| Contradiction `warning` non-overridden | cap `EXCLUSION_RANG_B_SCORE_CAP` (70) + entrée `elements_errones` libellée "Incohérence : A et B sont normalement incompatibles" |
| Contradiction overridden | AUCUN effet score ; visible uniquement en debug/rapport |

Deux nouveaux seuils dans `scoring_thresholds.py` ? **Non** — on
réutilise les deux caps existants (cohérent : une contradiction interne
error est une faute de même gravité qu'affirmer un concept FORBIDDEN
rang A). Si la calibration P4.2 montre qu'il faut des caps distincts, on
les séparera à ce moment-là.

Le feedback pédagogique reçoit la liste des contradictions actives pour
formuler l'explication (même canal que les exclusions golden actuelles —
le garde-fou anti-contradiction de formulation de P3 reste en aval).

### 3.1 Lien avec P4.1 (adéquation / sécurité)

`List[Contradiction]` est exactement l'entrée de la future dimension
sécurité. Le design prévoit donc :
- `check_response_coherence` renvoie une structure autonome, PAS un score ;
- `neuro_grader` applique les caps (comportement P4.1-avant) ;
- quand P4.1 arrivera, les caps seront remplacés par le score de sécurité
  séparé SANS toucher à `coherence.py`.

## 4. Impacts sur l'existant (analyse de non-régression)

### 4.1 `build_negation_map()` (scoring_v3, lignes 191-227)

Fonction actuelle : construit le mapping absent(patho)→concept-normalité
à partir des `excludes` + `excludes_families`. **Migrer 24 relations hors
de `excludes` change ce mapping.**

Vérification requise AVANT migration : lister les entrées de la negation
map qui proviennent des 24 relations DEFAULT. Options :
- (a) `build_negation_map` lit `excludes` **ET** `conflicts_by_default`
  (les deux expriment une opposition exploitable pour la conversion
  absent→positif) — **recommandé** : zéro régression, un mot à changer ;
- (b) figer la map et auditer entrée par entrée — coûteux, différé.

→ Choix proposé : **(a)**, avec un script de diff avant/après migration
(`_diff_negation_map.py`) qui doit être VIDE.

### 4.2 `_check_excludes()` (scoring_v3, lignes 274-303)

Utilisé pour le verdict `excluded` d'un concept attendu (réponse vs
golden). Même raisonnement : après migration, il doit voir
`excludes` + `conflicts_by_default` pour conserver le comportement
actuel (le contexte y est déjà golden-aware puisque le concept attendu
vient du golden). Un helper commun :

```python
def get_opposition_ids(concept: dict) -> List[str]:
    return (concept.get("excludes") or []) + (concept.get("conflicts_by_default") or [])
```

utilisé par `build_negation_map`, `_check_excludes` et le registry.

### 4.3 `negation_of`

Aucun changement moteur : le crédit déclaratif (bloc 1e) et
`NEGATION_CREDIT=0.0` gelé restent tels quels. La seule action (étape 2
du plan) est ONTOLOGIQUE : vérifier que les paires #1-4 portent bien
`negation_of` en plus de `excludes` (elles expriment les deux).

### 4.4 OWL

Nouveau champ `conflicts_by_default` : nécessite une **ObjectProperty
OWL nouvelle** (ex. label "conflit_par_defaut") + migration des 24
axiomes `exclut` existants vers cette propriété. Même pattern de patch
que `remove_false_excludes_from_owl_2026_08_11.py` (regex sur les blocs
Restriction, backup, dry-run) + mise à jour du mapping
`convert_owl_to_v2.py` (ligne 20-21 : ajout de l'IRI de la nouvelle
propriété → "conflicts_by_default").
