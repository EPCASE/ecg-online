## 1. Modèle de données

### 1.1 Ontologie (`ontology_v2.json`) — par concept

| Champ | Direction | Sémantique | Sévérité |
|---|---|---|---|
| `negation_of: [ids]` | directionnel (existant) | "ce concept EST la négation de X" | — (sert au crédit, PAS une contrainte à part) |
| `excludes: [ids]` | **symétrique** | contradiction absolue (13 relations HARD) | `error` |
| `conflicts_by_default: [ids]` | **symétrique** (nouveau champ) | incompatibilité clinique habituelle (24 relations DEFAULT) | `warning` |
| `excludes_families: [ids]` | symétrique sur la descendance (existant) | famille entière exclue (ECG_NORMAL…) | `error` (inchangé) |

- Symétrie : une seule déclaration suffit (`A.excludes = [B]` implique
  `B exclut A`). Le moteur canonicalise ; les réciproques déclarées en
  double dans le JSON sont tolérées (dédupliquées au chargement).
- Aucun champ `exceptions:` dans l'ontologie (l'override golden suffit).

### 1.2 Golden (par cas) — statut d'un concept

Trois statuts dérivés du golden existant, **sans modifier son format** :

```text
ACCEPTED   le concept (ou un descendant/parent proche crédité) figure au
           mapping du cas avec statut present (validant / complementaire /
           descripteur)
FORBIDDEN  le concept figure au golden avec statut "absent" (V1) ou
           role "exclusion" (V2)
UNKNOWN    le concept n'apparaît pas dans le golden du cas
```

Champ optionnel nouveau, par cas, ajouté SEULEMENT au besoin :

```json
"allowed_cooccurrences": [["QRS_FINS", "BLOC_DE_BRANCHE"]]
```

(couvre le cas où deux concepts sont légitimes ensemble sur CE tracé mais
où l'un des deux n'a pas vocation à être exigé dans la correction.)

## 2. Nouveau module : `rag_pipeline/coherence.py`

Un module dédié, séparé de `scoring_v3.py` (qui reste le calcul
d'adéquation). ~150 lignes estimées.

### 2.1 Chargement des contraintes (canonicalisation)

```python
@dataclass(frozen=True)
class Constraint:
    pair: Tuple[str, str]          # tuple(sorted((A, B))) — canonique
    kind: str                      # "excludes" | "conflicts_by_default"
    severity: str                  # "error" | "warning"

def build_constraint_registry() -> Dict[Tuple[str, str], Constraint]:
    """Parcourt l'ontologie une fois ; canonicalise et déduplique.
    En cas de double déclaration contradictoire (A excludes B ET
    A conflicts_by_default B) : garde la plus sévère + log warning."""
```

Cache module-level (même pattern que `_NEGATION_MAP`).

### 2.2 Statut golden d'un concept

```python
def golden_status(concept_id, case_golden) -> str:  # ACCEPTED|FORBIDDEN|UNKNOWN
```

Règles :
- **ACCEPTED = concepts explicitement `present` dans le golden du cas,
  UNIQUEMENT** (V1 stricte). Pas de fermeture par descendants : si le
  golden contient BLOC_DE_BRANCHE, cela n'affirme PAS que
  BLOC_DE_BRANCHE_DROIT est vrai — un parent ne rend pas ses descendants
  vrais. (Le crédit V3 enfant-plus-spécifique est une politique de
  NOTATION, pas une affirmation de vérité.) Extension possible APRÈS
  tests, et dans le seul sens logiquement valide : golden =
  BLOC_DE_BRANCHE_DROIT → ses ANCÊTRES (BLOC_DE_BRANCHE) peuvent être
  ACCEPTED.
- FORBIDDEN si statut "absent" / role "exclusion".
- UNKNOWN sinon — et **UNKNOWN ≠ faux** (monde ouvert : l'absence du
  golden n'est pas une affirmation de fausseté).

### 2.3 Évaluation des contradictions intra-réponse

```python
@dataclass
class Contradiction:
    concept_a: str
    concept_b: str
    kind: str          # excludes | conflicts_by_default
    severity: str      # error | warning
    status: str        # "active" | "overridden" | "data_inconsistency"
    detail: str        # "golden_accepts_both" | "allowed_cooccurrence"
                       # | "confirmed_by_golden_forbidden" | ""

def check_response_coherence(
    found_present: Set[str],       # concepts extraits statut=present UNIQUEMENT
    case_golden: dict,
) -> List[Contradiction]:
```

**Trois états, pas deux** — un HARD ne peut JAMAIS être levé
silencieusement (ni par le golden, ni par `allowed_cooccurrences`) :
si le golden accepte les deux pôles d'un `excludes` HARD, ce n'est pas
une exception clinique, c'est une **incohérence ontologie↔golden** à
remonter en alerte d'audit, sans pénaliser l'étudiant.

Algorithme central (version corrigée par l'expert) :

```text
pour chaque paire (A, B) de found_present × found_present, A < B :
    c = registry.get((A, B))
    si c est None : continuer

    si c.kind == "excludes" (HARD) :
        si golden accepte explicitement A ET B :
            → status=data_inconsistency        # alerte audit URGENTE
              (ne PAS pénaliser l'étudiant)
        sinon :
            → status=active, severity=error    # cap 25

    si c.kind == "conflicts_by_default" (DEFAULT) :
        si golden accepte explicitement A ET B :
            → status=overridden (golden_accepts_both)
        sinon si (A, B) ∈ allowed_cooccurrences :
            → status=overridden (allowed_cooccurrence)
        sinon si golden interdit explicitement A ou B (FORBIDDEN) :
            → status=active (confirmed_by_golden_forbidden)
              # la PÉNALITÉ vient déjà du circuit d'exclusion golden
              # existant — pas de double sanction ici
        sinon (golden UNKNOWN) :
            → status=active, severity=warning
              # feedback pédagogique + future dimension sécurité P4.1
              # AUCUN cap de score en V1 (monde ouvert : UNKNOWN ≠ faux)
```

Points de design :
- **Seuls les concepts `statut="present"` participent** — un concept nié
  ("pas de bloc de branche") ou en hypothèse ne contredit rien. (Une
  advisory `hypothese × present` pourra exister plus tard, pas en V1.)
- `allowed_cooccurrences` sur une paire HARD = **interdit**, vérifié par
  le CI (étape F).
- Complexité : |found| ≤ ~15 concepts par réponse → 105 paires max,
  lookup O(1) — négligeable.
- Les contradictions overridden/data_inconsistency sont **retournées
  quand même** (traçables dans les rapports/audits) mais n'ont aucun
  effet de score étudiant.

## 3. Effets sur le score (intégration `neuro_grader.py`)

| Événement | Effet score | Effet feedback |
|---|---|---|
| HARD `active` (error) | cap `EXCLUSION_RANG_A_SCORE_CAP` (25) + `correspondance="incorrecte"` + `elements_errones` | formulation catégorique (§3.2) |
| HARD `data_inconsistency` | **AUCUN** (l'étudiant n'y est pour rien) | aucun ; **alerte d'audit urgente** (log + rapport admin) |
| DEFAULT `active` confirmé par golden FORBIDDEN | **AUCUN cap supplémentaire** — la pénalité vient déjà du circuit d'exclusion golden existant (pas de double sanction) | mention dans le feedback |
| DEFAULT `active` golden UNKNOWN | **AUCUN cap en V1** (monde ouvert : UNKNOWN ≠ faux) ; alimente la future dimension sécurité P4.1 | formulation prudente (§3.2) |
| `overridden` | AUCUN | aucun ; visible en debug/rapport |

Pas de nouveaux seuils dans `scoring_thresholds.py` : seul le cap 25
existant est réutilisé (HARD actif). **Le cap 70 n'est PAS appliqué aux
DEFAULT** — le résoudre autrement produirait des faux positifs sur les
ECG complexes réels pour satisfaire un challenge synthétique.

Conséquence assumée : **chal_02 sera DÉTECTÉ (warning tracé + feedback)
mais sa note ne chute pas encore** tant que le cas ne documente pas le
conflit (golden UNKNOWN sur RYTHME_REGULIER). Il alimentera la dimension
sécurité P4.1 — c'est le bon canal.

### 3.2 Formulations feedback

- HARD : « Contradiction : vous affirmez à la fois A et B, qui ne peuvent
  pas décrire simultanément le même élément du tracé. »
- DEFAULT : « À vérifier : vous décrivez à la fois A et B. Cette
  association est habituellement incohérente s'ils décrivent le même
  élément ou la même séquence du tracé, mais peut être possible dans
  certains contextes. »

(fidèle à ce que le moteur sait réellement — pas de certitude simulée.)

### 3.1 Lien avec P4.1 (adéquation / sécurité)

`List[Contradiction]` est exactement l'entrée de la future dimension
sécurité. Le design prévoit donc :
- `check_response_coherence` renvoie une structure autonome, PAS un score ;
- `neuro_grader` applique les caps (comportement P4.1-avant) ;
- quand P4.1 arrivera, les caps seront remplacés par le score de sécurité
  séparé SANS toucher à `coherence.py`.

## 4. Impacts sur l'existant (analyse de non-régression)

### 4.1 Séparation stricte des trois usages — PAS de helper commun

**Correction expert : `conflicts_by_default` n'est PAS une négation.**
`BRADYCARDIE conflicts_by_default TACHYCARDIE` n'autorise pas
`absent(BRADYCARDIE) → TACHYCARDIE`. Confondre relation de CRÉDIT et
relation de VÉRITÉ clinique réintroduirait le couplage qu'on enlève.

Cible architecturale (trois accès distincts, pas de
`get_opposition_ids` commun) :

| Consommateur | Lit |
|---|---|
| `build_negation_map()` | **`negation_of` uniquement** (cible) ; transition : `negation_of` + legacy `excludes` HARD non migrés, fallback supprimé une fois les vrais couples de négation déclarés |
| `_check_excludes()` | `excludes` + `excludes_families` uniquement (HARD) — il tourne AVANT le match et sans `case_golden`, lui faire lire les DEFAULT court-circuiterait l'override |
| registry `coherence.py` | `excludes` + `conflicts_by_default` + `excludes_families` |

Le critère « diff negation map = vide » est REJETÉ comme critère absolu :
si l'ancienne map contenait des inférences douteuses issues des anciens
excludes, une différence est SOUHAITABLE. Le script `_diff_negation_map.py`
produit le diff → **audit du diff par l'expert**, pas exigence de nullité.

### 4.2 `_check_excludes()` (scoring_v3, lignes 274-303)

Reste sur `excludes` + `excludes_families` UNIQUEMENT (cf. §4.1). Après
migration, les 24 relations DEFAULT ne déclenchent plus le verdict
`excluded` — c'est VOULU : ces relations n'expriment pas une
impossibilité, et ce chemin de code n'a pas accès au golden pour
arbitrer. Les conséquences (perte de quelques verdicts `excluded`
"chanceux") sont mesurées par le challenge set + diff sur
`extraction_golden.json` à l'étape B.

### 4.3 `negation_of`

Aucun changement moteur : le crédit déclaratif (bloc 1e) et
`NEGATION_CREDIT=0.0` gelé restent tels quels. La seule action (étape 2
du plan) est ONTOLOGIQUE : vérifier que les paires #1-4 portent bien
`negation_of` en plus de `excludes` (elles expriment les deux).

### 4.4 OWL

Nouveau champ `conflicts_by_default` : nécessite une **ObjectProperty
OWL nouvelle** (ex. label "conflit_par_defaut") + migration des 24
axiomes `exclut` existants vers cette propriété. Même pattern de patch
que `remove_false_excludes_from_owl_2026_08_11.py` (regex sur les blocs
Restriction, backup, dry-run) + mise à jour du mapping
`convert_owl_to_v2.py` (ligne 20-21 : ajout de l'IRI de la nouvelle
propriété → "conflicts_by_default").
