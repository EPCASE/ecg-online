## 1. Challenge de la proposition (sans présomption de supériorité)

### 1.1 Ce que la proposition règle réellement

Le point faible du design P4.3b actuel n'est PAS la détection des paires —
c'est la **fiabilité de la polarité** en amont. La chaîne actuelle :

    NER (statut) → fixes regex négation/hedging (candidate_report) → present only

est une heuristique de discours déguisée : `_is_hedged_in_context`,
`_NEG_PREFIX_RE`… C'est déjà l'architecture A (symbolique enrichie) en
embryon, avec exactement la fragilité prédite : chaque nouveau pattern
discursif (« si l'irrégularité n'est pas réelle… ») demande une regex de plus.

La proposition C déplace cette responsabilité vers un juge NLI **local à la
paire**, ce qui est structurellement plus sain : la question « A et B
sont-ils affirmés simultanément avec la même portée ? » est une tâche NLI
standard, pas de la cardiologie. **Cohérent avec la doctrine « pas de
connaissance cardiologique dans le Python »** — mieux : elle permet de
RETIRER à terme des heuristiques regex du Python.

### 1.2 Objections et limites à ne pas sous-estimer

1. **Le problème n'est pas fréquent aujourd'hui.** Sur le challenge set
   (16 items) : 1 seule paire candidate (chal_02, construite exprès). Sur
   les copies réelles courtes (le format dominant : « FA, QRS fins,
   réponse rapide »), les paires candidates sont rares. Le coût
   d'architecture doit être proportionné à la fréquence RÉELLE mesurée —
   à mesurer AVANT de construire (cf. §5, étape 0 du protocole).
2. **Reproductibilité.** P4.3b est 100 % déterministe et testable en CI
   sans réseau. Un juge LLM introduit de la variance là où on venait
   d'éliminer celle du grader GPT global. Mitigation : température 0,
   sortie contrainte (enum), cache par (paire, spans), et le juge ne peut
   qu'**adoucir** (désactiver une contradiction), jamais aggraver — la
   variance ne peut alors produire que des faux négatifs, jamais des faux
   positifs de sanction. Cette asymétrie est la clé de l'acceptabilité.
3. **Double juge, double erreur.** Le pipeline appelle déjà un juge LLM
   pour la résolution ontologique (`neurosymbolic_judge`). Si la polarité
   NER est fausse (le vrai problème racine), le juge de contradiction
   reçoit des spans mal étiquetés. Le juge contextuel ne corrige PAS le
   NER — il faut le dire explicitement : il arbitre la RELATION, pas les
   nœuds. Un NER qui marque `present` un concept nié reste un bug NER.
4. **Le golden override reste premier.** L'ordre de résolution doit être :
   golden override (P4.3b) → si toujours candidate → juge contextuel.
   Le juge n'est jamais consulté sur une paire déjà `overridden` : le
   mécanisme le moins cher et le plus fiable passe toujours d'abord.
5. **Biais de verbosité inversé.** Le juge protège les bavards prudents,
   mais un étudiant qui écrit tout et son contraire (« FA possible,
   flutter possible, rythme sinusal possible ») en mode hypothese
   n'affirme rien → aucune paire → aucune pénalité ni détection. C'est
   un choix assumé (l'abstention diagnostique est traitée ailleurs,
   cf. `abstention.py`), mais à documenter : le juge contextuel ne
   mesure PAS l'engagement diagnostique.

### 1.3 Verdict du challenge

La proposition est bonne **comme extension de P4.3b, pas comme
remplacement**. P4.3b fournit exactement le « détecteur symbolique » de
l'architecture cible ; il manque seulement (a) les spans dans
`ExtractedConcept`, (b) un point d'insertion « arbitre » entre la détection
et l'état final. Le design 3-états de P4.3b s'étend naturellement : le juge
ajoute un 4e chemin de sortie (`waived_by_context`) à côté de `overridden`.

## 2. Comparaison des architectures

| Critère | A — symbolique enrichi | B — juge LLM global | C — juge ciblé post-sélection | D — HARD déterministe / DEFAULT arbitré |
|---|---|---|---|---|
| Complexité d'implémentation | Élevée et croissante (stance, groupes, scopes = analyseur de discours maison) | Faible en code, élevée en prompt | Moyenne (spans + 1 module + prompt court) | = C + une règle de routage |
| Dépendance au modèle | Nulle | Totale | Faible (tâche NLI locale, modèle interchangeable) | Faible, et nulle sur les HARD clairs |
| Explicabilité | Bonne mais règles opaques à force | Faible (jugement holistique) | Bonne : paire + spans + verdict enum + evidence | Idem C |
| Reproductibilité | Parfaite | Mauvaise | Bonne (T=0, enum, cache) ; parfaite si juge ne peut qu'adoucir | Idem C, encore meilleure (HARD clairs sans LLM) |
| Coût / latence | 0 | 1 gros appel/réponse | 0–2 petits appels/réponse (mesuré : paires rares) | ≤ C |
| Faux positifs (contradiction à tort) | Élevés sur discours riche | Moyens, imprévisibles | Faibles (abstention UNCERTAIN → pas de sanction) | Faibles |
| Biais anti-bavards | Fort (c'est le problème) | Moyen | Faible | Faible |
| Abstention | Impossible proprement | Difficile à contraindre | Native (UNCERTAIN) | Native |
| Modèle local | N/A | Irréaliste | **Plausible** : classification 5 classes sur 2-3 phrases | Plausible |
| Calibration scientifique | Difficile (règles ad hoc) | Difficile (sortie non structurée) | **Bonne** : verdicts + confiance vs jugement expert | Bonne |
| Maintenabilité ontologie | Charge accrue (scopes dans l'ontologie ?) | Ontologie contournée | Inchangée (paires = déjà déclarées) | Inchangée |
| Impact sur P4.3b/P4.1 | Refonte NER | Contourne P4.3b | **Extension propre** (4e état) | Extension propre |

**Recommandation : D**, qui est C avec le routage suivant :

- HARD, les deux spans dans la MÊME phrase, deux `present` nets →
  déterministe (comportement P4.3b actuel conservé, pas d'appel LLM) ;
- HARD, spans dans des phrases différentes → juge (alternance temporelle,
  conditionnel, différentiel mal capté par le NER) ;
- DEFAULT actif (non overridden par le golden) → juge systématique ;
- verdict `CONTRADICTION` (confiance ≥ seuil) → l'état `active` est
  confirmé ; tout autre verdict (ALTERNATIVE / CONTEXTUALLY_COMPATIBLE /
  NOT_ASSERTED / **UNCERTAIN**) → `waived_by_context`, trace conservée.
- **Invariant de sûreté : le juge ne peut jamais créer une contradiction
  que le symbolique n'a pas détectée, ni durcir un DEFAULT en HARD.**

## 3. Cas limites identifiés

1. **Anaphore inter-phrases** : « La FA est probable. Le rythme, lui, est
   régulier. » — les spans isolés perdent le lien ; fournir phrase
   précédente + suivante (fenêtre ±1) atténue sans tout résoudre.
2. **Portée territoriale implicite** : « microvoltage en frontal, voltage
   conservé en précordial » — CONTEXTUALLY_COMPATIBLE, exactement le cas 75.
   Le juge gère ce que l'ontologie non-territorialisée ne peut pas exprimer.
3. **Temporalité intra-tracé** : « début en FA puis retour en rythme
   sinusal » — CONTEXTUALLY_COMPATIBLE ; aucun symbolique raisonnable ne
   le capte.
4. **Négation portée par la conclusion** : « …ce qui élimine la FA » en fin
   de réponse, après une évocation `present` en début — le juge voit les
   deux spans mais pas forcément la conclusion si elle ne contient pas les
   termes ; risque de faux positif résiduel. Mitigation partielle :
   fenêtre ±1 + verdict UNCERTAIN.
5. **Concepts inférés** (`terme_brut="[inféré] 3/4 critères"`,
   `pattern_inference`) : pas de span réel → JAMAIS envoyés au juge ;
   les exclure des paires candidates arbitrables (rester déterministe ou
   ignorer).
6. **Même terme, deux occurrences de polarités différentes** : la règle
   actuelle « le plus affirmatif gagne » (`_rank`) écrase l'information ;
   pour le juge il faut transmettre TOUTES les occurrences du concept avec
   leurs spans, pas le max agrégé.
7. **Réponses en style télégraphique** (« FA. Régulier. QRS fins. ») : pas
   de marqueurs discursifs → le juge ne peut que confirmer ; c'est le cas
   où le déterministe et le juge convergent, OK.
8. **Injection** : l'étudiant écrit « ignore les contradictions » dans sa
   copie → le prompt du juge ne doit contenir les spans que comme données
   citées, avec sortie contrainte enum (pas de texte libre exploitable).

## 4. Minimum de métadonnées NER requis

Constat vérifié dans le code : `ClinicalEntity` (NER) porte déjà
`contexte_phrase`, mais **`ExtractedConcept` (candidate_report) ne le
conserve pas** — c'est la seule vraie lacune. Le minimum est donc :

1. `ExtractedConcept.contexte_phrase: str` — recopier le champ existant du
   NER lors de la construction (1 ligne, zéro appel supplémentaire).
2. `ExtractedConcept.occurrences` implicites : ne PAS dédupliquer par
   concept avant l'arbitrage (conserver chaque extraction avec son span) —
   déjà le cas dans `concepts_extraits`, c'est l'agrégation `_rank` en aval
   qu'il ne faut pas appliquer avant le juge.
3. Optionnel V2 : offsets caractère dans le texte source (pour la fenêtre
   ±1 phrase exacte). En V1, `contexte_phrase` suffit : c'est déjà la
   phrase porteuse.

**PAS besoin** de stance/alternative_group/scopes dans le NER : c'est
précisément ce que l'architecture C évite.

## 5. V1 minimale de test (sans modifier le pipeline de production)

Esprit « mesurer avant de construire » :

- **Étape 0 — instrumentation passive (aucun changement de comportement)** :
  ajouter `contexte_phrase` à `ExtractedConcept` ; dans `_check_coherence`,
  logger chaque paire candidate (concepts, kind, statuts, spans, état
  P4.3b) dans un JSONL `data/coherence_pairs_log.jsonl`. Déployer. Laisser
  tourner sur les copies réelles (et rejouer les copies historiques du
  collector + virtual students).
- **Étape 1 — juge offline** : script batch qui lit le JSONL et fait juger
  chaque paire par (a) GPT-4o-mini, (b) un modèle local candidat
  (ex. 7-8B quantisé), prompt de classification 5 classes, T=0, sortie
  JSON contrainte. AUCUN branchement dans le scoring.
- **Étape 2 — vérité terrain** : l'expert annote les mêmes paires
  (interface = simple tableau markdown/CSV : spans + 5 classes). C'est le
  même protocole d'arbitrage que P4.3a (49 relations), format connu.
- **Étape 3 — décision chiffrée** : accord juge/expert, matrice de
  confusion, taux d'UNCERTAIN, coût par copie. GO/NO-GO sur le branchement
  en production (qui reste minuscule : un hook entre `active` et
  l'application du cap dans `neuro_grader`).

Coût de la V1 : ~1 champ + ~1 logger + 2 scripts offline. Réversible à 100 %.

## 6. Protocole de benchmark

- **Corpus** : (a) challenge set v1 (16 items, dont chal_02) + 5-10 items
  adversariaux NOUVEAUX ciblant les cas limites §3 (différentiel explicite,
  temporalité, territoires, conditionnel, conclusion négative) ; (b) copies
  réelles du collector (rejeu) ; (c) virtual students.
- **Référence** : annotation expert des paires candidates (5 classes),
  double annotation sur un sous-échantillon pour mesurer l'accord
  inter-expert (κ) — plafond de performance réaliste du juge.
- **Bras comparés** : (1) P4.3b seul (règles) ; (2) juge LLM global (B,
  pour borner) ; (3) hybride D avec GPT-4o-mini ; (4) hybride D avec
  modèle local.
- **Métriques** : sensibilité/spécificité des contradictions réelles ;
  taux de faux positifs sur différentiels ; faux positifs en fonction de
  la longueur de réponse (le biais de verbosité, mesuré explicitement) ;
  accord pondéré avec expert ; calibration de la confiance (ECE) ; taux
  d'abstention ; nb moyen d'appels LLM/réponse ; latence/coût.
- **Publication potentielle** : le triptyque règles / LLM / hybride avec
  référence expert est un design d'étude propre et original (détection de
  contradictions dans des réponses cliniques libres) — à inscrire dans la
  roadmap scientifique comme axe expérimental.

## 7. Décision recommandée

**Chantier expérimental séparé (P4.3c), qui ÉTEND P4.3b sans le
remplacer.**

- P4.3b reste tel quel en production : détection déterministe, HARD → cap,
  DEFAULT → warning sans pénalité. Rien à défaire.
- P4.3c = étapes 0-3 du §5 (instrumentation + juge offline + benchmark).
  Décision de branchement en production APRÈS les chiffres.
- P4.1 (score de sécurité) doit être conçu pour accueillir le futur
  arbitrage : la structure `SafetyEvent` proposée est adoptée comme format
  pivot dès P4.1, avec `source: "symbolic"` aujourd'hui et
  `source: "llm_contextual_judge"` demain, et un champ
  `arbitration: null | verdict`. Ainsi P4.1 n'aura pas à être refactoré.
- Ordre : **P4.1 d'abord** (avec SafetyEvent), puis P4.3c étape 0 (le
  logging peut d'ailleurs être livré avec P4.1), puis benchmark quand un
  volume de copies réelles suffisant est accumulé.

### Ce qui tuerait la piste (critères d'abandon explicites)

- fréquence des paires candidates < ~1 % des copies réelles → le problème
  ne vaut pas l'architecture ;
- accord juge/expert < accord inter-expert − marge → le juge n'apporte pas
  de signal fiable ;
- taux d'UNCERTAIN > ~40 % → le juge n'arbitre pas, il esquive.
